# План: кнопки «О чем статья?», «Тезисы», «Пост для Telegram»

Основание: [PROJECT.md](./PROJECT.md).

Приложение получает URL англоязычной статьи, парсит её и по нажатию кнопки подключает AI для генерации нужного вида ответа в блоке «Результат».

**Текущее состояние:** парсинг и кнопка «Перевести» работают; три кнопки действий — заглушки в `referent-app.tsx`.

---

## 1. Зафиксировать требования к каждой кнопке

Перед кодом описать ожидаемый результат для пользователя:

| Кнопка | Что должно появиться в «Результат» |
|--------|-------------------------------------|
| **О чем статья?** | Краткий пересказ статьи на русском (не полный перевод): главная мысль, контекст, выводы |
| **Тезисы** | Список ключевых мыслей статьи на русском (5–10 пунктов) |
| **Пост для Telegram** | Готовый к публикации пост на русском (до ~1000 символов) |

Общий сценарий для всех трёх кнопок (как в PROJECT.md):

1. Пользователь вводит URL.
2. Нажимает одну из кнопок.
3. Приложение парсит статью.
4. AI генерирует ответ нужного типа.
5. Ответ показывается в блоке «Результат» с соответствующим бейджем.

## 2. Расширить типы и промпты AI (`lib/ai-actions.ts`)

1. Расширить `AiAction`: добавить `"summary"`, `"theses"`, `"telegram"` (сейчас только `"translate"`).
2. Для каждого действия задать **отдельный system-промпт** — чтобы модель не смешивала форматы.
3. Для каждого действия задать **отдельную user-инструкцию** с чёткой структурой ответа:
   - `summary` — заголовок + раздел «О чём статья», без полного перевода текста;
   - `theses` — заголовок + раздел «Тезисы», только список мыслей;
   - `telegram` — готовый пост (заголовок, ввод, пункты), без перевода всей статьи. Добавить в конце поста ссылку на источник.
4. Явно запретить в промптах лишний контент: «не переводи статью целиком», «отвечай только …».
5. Переиспользовать существующую функцию `buildArticlePayload` и `buildTranslationMessages`.

## 4. Подключить кнопки в интерфейсе (`app/components/referent-app.tsx`)

1. Удалить заглушки: константу `ACTION_STUBS` и функцию `handleActionStub`.
2. Вынести общую логику обработки в одну функцию (например, `runAction(action)`):
   - проверка URL;
   - сброс предыдущего результата;
   - установка бейджа (`RESULT_BADGES[action]`) и подсветки активной кнопки;
   - парсинг через `fetchArticle` → `/api/parse`;

3. Кнопку **«Перевести»** оставить отдельным вызовом с `action: "translate"` — поведение не менять.
4. Три кнопки действий привязать к `runAction("summary" | "theses" | "telegram")`.
5. Сохранить защиту от гонки (`requestIdRef`) — при быстром переключении кнопок старый ответ не должен перезаписывать новый.
6. Сохранить обработку недоступных статей через `ArticleUnavailableError` (мягкое сообщение в блоке «Результат»).

## 6. Проверить на реальных статьях

Прогнать каждую кнопку на 2–3 URL:

1. Обычная статья (блог, новость) — все три формата дают разный, но корректный результат.
2. Статья с ограниченным доступом (403) — дружелюбное сообщение, без красной ошибки под полем URL.
3. Быстрое переключение между кнопками — в «Результат» попадает ответ последней нажатой кнопки.

Критерии приёмки:

- «О чем статья?» — только краткий пересказ, без полного перевода.
- «Тезисы» — только список тезисов.
- «Пост для Telegram» — только готовый пост, пригодный для публикации.
